Events record what a customer does in your product, such as using a feature or connecting an integration. Each event belongs to one customer and feeds the [usage summary](/guides/usage-analytics).

## Track an event

Send `POST /events` with the customer ID and an event name:

```bash
curl -X POST http://localhost:8787/v1/events \
  -H "Authorization: Bearer ns_demo_key" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: evt-dashboard-2026-11-16-001" \
  -d '{
    "customer_id": "cus_7a2b9c",
    "name": "feature.used",
    "properties": { "feature": "dashboard", "source": "web" },
    "occurred_at": "2026-11-16T16:20:00Z"
  }'
```

A `201 Created` response returns the stored event:

```json
{
  "id": "evt_89fa2d",
  "customer_id": "cus_7a2b9c",
  "name": "feature.used",
  "properties": { "feature": "dashboard", "source": "web" },
  "occurred_at": "2026-11-16T16:20:00Z",
  "received_at": "2026-11-16T16:20:01Z"
}
```

### Request fields

| Field | Required | Description |
| --- | --- | --- |
| `customer_id` | Yes | ID of an existing customer. An unknown ID returns `404`. |
| `name` | Yes | Non-empty event name, such as `feature.used`. |
| `properties` | No | Object of free-form key-value pairs. Defaults to `{}`. |
| `occurred_at` | No | ISO 8601 timestamp of when the action happened. Defaults to the server clock when omitted. |

The response adds `id` and `received_at`, the time Northstar stored the event. Usage summaries count events by `occurred_at`, so send it when you track activity after the fact, such as when replaying a queue.

## Name events consistently

An event name should be stable over time. Changing names splits one activity across two names in your usage summaries.

- Use a `noun.verb` pattern in lowercase, such as `feature.used` or `user.invited`.
- Put variable details in `properties`, not in the name. Track `feature.used` with `{"feature": "dashboard"}` rather than `dashboard.used`.
- Document the property keys for each event and keep their types the same.

The [Customer onboarding recipe](/guides/customer-onboarding#recommended-tracking-plan) includes an example tracking plan.

## Retry safely

Send an `Idempotency-Key` header so a retried request does not store the same event twice. Keys can be up to 128 characters.

- Retrying with the same key and the same body returns the original response.
- Reusing a key with a different body returns `409 Conflict`.

See [Pagination and rate limits](/guides/pagination#retry-strategy) for which errors to retry.

## List recent events

`GET /events` returns events newest first. Filter to one customer with `customer_id`:

```bash
curl 'http://localhost:8787/v1/events?customer_id=cus_7a2b9c&limit=20' \
  -H "Authorization: Bearer ns_demo_key"
```

The response uses [cursor pagination](/guides/pagination#cursor-pagination): read `data`, then request the next page with `pagination.next_cursor` while `pagination.has_more` is `true`.

## Errors

| Status | Cause |
| --- | --- |
| `400` | The body is not valid JSON or `Content-Type` is not `application/json`. |
| `404` | `customer_id` does not match an existing customer. |
| `409` | The `Idempotency-Key` was already used with a different body. |
| `422` | `customer_id` or `name` is missing, `name` is empty, `properties` is not an object, or `occurred_at` is not an ISO 8601 timestamp. |
